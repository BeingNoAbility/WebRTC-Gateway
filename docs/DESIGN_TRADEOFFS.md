# 设计边界、架构权衡与工程模式 (Design Boundaries & Trade-offs)

> **文档分层与优先级**：[核心原则](./CONSTITUTION.md) > [审查清单](./REVIEW_GUIDELINES.md) > 本文。
>
> 为避免把当下版本的工程权衡误当作永久教条，同时也防止已被证伪的设计反复回归，本文严格区分三类知识：① **不可触碰的永久 Non-Goals**；② **当前架构权衡及允许经 RFC 重评的前提条件**；③ **跨层反复出现的典型陷阱模式**。当前实现的具体协议常量与默认参数见 [协议规范](./guide/protocol-specification.md) 与 [安全机制](./guide/security.md)。

## 一、永久 Non-Goals（定位与安全物理红线）

以下 4 类方向直接违背项目定位或浏览器/密码学安全物理，不属于权衡取舍，审查中应当直接拒绝：

### 1. 中心数据中继与信令侧离线口令预言机

- **为何拒绝**：在信令服务器缓存、解码或转发业务流量会彻底背离“零数据中继”定位；在信令消息中携带口令哈希或数据面会话句柄，会让信令观察者或日志泄漏者获得无限速率的离线暴破预言机。
- **边界**：信令仅撮合连接；端点验签与访客鉴权只在端到端加密传输通道内执行；对称 NAT 回退仅允许用户自建、只转发端到端密文的 TURN。

### 2. 把页面内 JS 补丁当作安全边界，或默认单源/同站共享真实 Cookie

- **为何拒绝**：浏览器内 `window.top`、`Document.prototype.cookie` 等原生原语不可在不可信页面内可靠伪造；同源或同站子域共享会引发 Cookie Tossing 与僵尸凭据残留。页面内脚本补丁只可作为兼容层，绝不能充当安全边界。
- **边界**：非回环默认由浏览器原生的跨站双域机制提供站点级隔离；服务端 `HttpOnly` Cookie 仅驻留于 Agent 侧隔离存储，客户端可读写 Cookie 通过纯内存镜像与代理侧分池同步，不污染真实浏览器 `document.cookie`。

### 3. 内置业务应用 UI、特定应用硬编码与进程内兼容插件

- **为何拒绝**：在门户或 Agent 内置网盘/终端界面、针对单个应用编写路径/头部特判，或开放进程内插件与沙箱 JS 补丁钩子，会破坏“透明管道”定位、扩大私钥与会话暴露面、锁死内部重构自由度，并掩盖本应修在标准层的共性缺陷。
- **边界**：严格按 [核心原则三步分流决策树](./CONSTITUTION.md#原则三-透明管道与应用中立) 分流——规范共性修入核心，通用反代能力以默认关闭开关提供，特定应用怪癖通过下游标准 HTTP/WS 边界（本地 Nginx / Caddy 或独立 Sidecar）组合解决。

### 4. 通用跨源开放代理、正则主机改写与运行时端点覆盖

- **为何拒绝**：内置跨源多域名代理会把单目标隧道扩张为通用反代与 SSRF 攻击面；前缀或正则主机猜测改写易造成源混淆；允许通过 URL 参数在运行时覆盖信令地址，或放宽门户内联脚本/样式策略，会直接打开钓鱼劫持与 XSS 攻击面。
- **边界**：严守“单 Agent = 单精确目标源”，URL 匹配基于标准 `URL` 精确源比较；门户坚持严格 CSP 与零运行时外部端点覆盖。

## 二、当前架构权衡与重评条件

以下 5 项是当前版本在浏览器能力、复杂度预算与运维可靠性约束下的**工程选择**，而非永恒定律。每项均标明“为何当下这么选”与“何种前提变化时欢迎通过 RFC 重评”：

### 1. 单连接有序信道池 vs 多连接聚合 / 跨信道拆流

- **当下选择**：单条 `RTCPeerConnection` 内组合分片控制通道与固定数量的预协商有序多路复用数据通道（按单调流 ID 统一承载 HTTP 与流式 WebSocket），用 SCTP 通道原生有序性替代跨流队头阻塞、动态 DCEP 竞态与复杂乱序重组。
- **为何当下不选多连接或跨信道拆流**：不同 SCTP 通道间无因果顺序，把头帧与数据帧拆道或维护多条并发 PC 会引入孤儿帧缓冲池、跨连接生命周期同步与严重的竞态/内存放大风险。
- **重评条件（RFC）**：当主流浏览器普遍稳定支持原生轻量级 P2P 多路复用传输（例如标准化 P2P WebTransport / QUIC Streams），或有可复现的生产工作负载证明单连接多路复用成为不可规避的瓶颈。

### 2. 重建连接静默重连 vs 原地 ICE Restart

- **当下选择**：网络切换或传输断开后，由门户在后台建立全新连接并用当前标签页内存派生的认证材料静默重认证，保持应用 iframe 挂载不重载。
- **为何当下不选原地 ICE Restart**：此前为配合原地重建引入的跨端加密棘轮与多状态机复杂度高、重放与失步面大，而重建新连接在常见交互式 HTTP 场景下延迟低且状态彻底归零。
- **重评条件（RFC）**：若能提出不依赖自研密钥棘轮、纯粹基于标准 RFC 8839 的极简 ICE Restart 方案，并在目标浏览器与底层 WebRTC 栈上稳定验证可跨蜂窝/Wi-Fi 切换保活长连接 WebSocket 与大文件上传，欢迎经 RFC 重评。

### 3. 单一权威信令二进制交付前端 vs 分离式静态托管 / 双栈信令

- **当下选择**：前端内容哈希资产由单一权威 Go `signal` 二进制按显式清单内嵌交付，并仅维护一套权威 Go 信令实现。
- **为何当下不选分离托管或双栈实现**：手工维护分离的静态 CDN、反代 CORS/CSP 与 SW 路由极易误配且在缺少密码学验证时并未真正缩减 TCB；同时手写维护两套不同语言的信令服务端会导致限流、路径规范化与并发边界持续漂移。
- **重评条件（RFC）**：当出现（a）无需脆弱手工配置的、可密码学验证的前端分发机制以实质缩减信令 TCB；或（b）能从单一事实源自动编译/生成多运行时部署目标并通过全部黑盒一致性测试套件时，可经 RFC 重评。

### 4. 零运行期第三方 JS 依赖 vs 第三方 JS / WASM 编解码与解析器

- **当下选择**：压缩协商优先复用浏览器原生流式能力（`DecompressionStream`）与语言标准库，HTML 注入采用零依赖字节级流式状态机。
- **为何当下不选第三方 JS/WASM 库**：纯 JS 解压器或重型 WASM 解析器会显著膨胀 Service Worker 产物体积与冷启动延迟，并在恶意高压缩比输入下增加 OOM 与供应链风险。
- **重评条件（RFC）**：当 Web 平台标准化更强的原生流式能力（如原生 HTML 重写器或更多原生压缩算法），或存在体积与内存上界均经过严格验证的最小化模块可解决原生实现无法覆盖的规范缺口。

### 5. 外部标准反代组合 vs 网关内置多源路由与响应改写

- **当下选择**：网关聚焦单精确目标的透明传输，多服务聚合、复杂路径改写与私有鉴权适配交由目标侧的本机 Nginx / Caddy 或独立 HTTP/WS Sidecar。
- **为何当下不内置复杂路由引擎**：标准 HTTP/WS 是天然进程隔离且零 API 锁死的扩展边界，既能复用成熟反代生态，又能避免扩展代码共享 Agent 私钥与会话存储。
- **重评条件（RFC）**：某项能力经验证属于跨应用通用、遵循 RFC 标准的纯代理原语时，按核心原则三步分流树的第 2 步以默认关闭的通用开关纳入核心。

## 三、跨层典型陷阱模式

下列 6 类陷阱在浏览器 P2P 代理栈中反复出现，审查与设计时应从**通用机理**出发举一反三，而非只记忆某一次具体补丁：

### 1. 解析差分与二次规范化绕过

- **通用机理**：不同引擎对自由文本协议（如原始 SDP）、百分号编码、混合 IPv4/IPv6 地址、冗余斜杠或软链接的解析存在差异；若校验与执行之间发生二次解码或路径重解，安全边界会被直接绕过。
- **防御原则**：用最小结构化契约替代自由文本正则解析；路径、Origin 与代理转发头只做单次规范化；IPv6 前缀聚合前先还原映射地址；文件系统访问依托内核句柄隔离（如逐级 `os.Root` 与单次无跟随打开）消除 TOCTOU。

### 2. 隐式元数据与底层容量放大

- **通用机理**：仅按载荷字节数计费无法挡住海量 0 字节/极小分片、子切片引用大底盘数组（堆放大）、高压缩比解压炸弹或整包缓冲大 WebSocket 消息造成的内存耗尽。
- **防御原则**：对长效缓存数据做等长拷贝消除底盘残留，将每条目固定结构开销纳入多层预算，采用固定缓冲 O(1) 流式转发与解压膨胀比硬顶，并在流关闭、重置或早响应退出时无条件归还预算与槽位。

### 3. 跨阻塞 I/O 持锁与异步代际竞态

- **通用机理**：在持有同步互斥锁时等待网络/通道读写，会在半截断连时演变为永久死锁；网络波动与重连期间，过期连接的异步回调、定时器或延迟帧可能污染新会话状态。
- **防御原则**：建立全局一致锁层级，取消/重置路径必须无锁唤醒阻塞 I/O；为会话与复用槽位引入单调代际号过滤过期回调与迟到帧；确保所有后台协程与资源在静默断网和停机时于有界时间内退出。

### 4. 浏览器合成执行与标准代理的语义落差

- **通用机理**：Service Worker 构造的合成响应失去浏览器部分默认处理——不会自动解压、遇到空体响应启动解压会抛异常、Fetch `Headers` 严格要求 ByteString、按文本块替换 HTML 会截断多字节 UTF-8 或把 `<meta charset>` 挤出预扫描窗口、在 `<!DOCTYPE>` 前插入标签会触发 Quirks Mode；对未知结果的非幂等请求自动重试还会引发重复写入。
- **防御原则**：按 W3C / IETF 规范显式处理空载荷、编码协商、RFC 5987 文件名净化与字节级 HTML5 状态机分词；自动重试严格限定于无体幂等请求；对 SSE、`206 Range` 与强 `ETag` 保持透明旁路。

### 5. 同源/同站权限混淆与不可信租户污染

- **通用机理**：将交互应用与不受信静态文档混用同套 CSP 会导致静态 HTML/SVG 存储型 XSS；让不可信页面脚本与服务端受保护会话共享单一 Cookie 池，会遭遇分号注入、同名覆盖或泛洪驱逐；在本地开发或跨站场景放宽 Origin/Fetch 校验会引入 CSRF 与跨站 WebSocket 劫持（CSWSH）。
- **防御原则**：始终将应用沙箱源视为不可信租户——对全部静态文件默认下发沙箱 CSP、按 RFC 6265bis 将服务端与客户端 Cookie 分池隔离、以 W3C Fetch 原生属性与精确 Origin 白名单实施抗 CSRF / CSWSH 门禁。

### 6. 限流饱和失效与非原子持久化丢写

- **通用机理**：限流表满时若回退为放行（Fail-Open）或淘汰仍处于活跃封禁期的条目，攻击者只需泛洪新键即可洗掉爆破锁定；并发非原子写文件会在崩溃或竞态下丢失密钥绑定与令牌吊销记录。
- **防御原则**：限流器饱和且无闲置项可回收时必须 Fail-Closed 且保护活跃锁定项；安全状态持久化统一使用单写者原子落盘（临时文件 + `fsync` + 原子重命名），并在活跃连接与请求入口持续执行吊销校验。
